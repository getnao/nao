Implement story-level filters in nao

Implement filters for stories: a filter bar at the top of a story that filters all charts/tables in the story whose underlying SQL is relevant to the filter, by rewriting each chart's SQL and re-executing it. Filters auto-apply to any chart whose query is relevant (default), and can also be explicitly linked to specific charts. Read CLAUDE.md and AGENTS.md first and follow the repo conventions (kebab-case files, tabs, no inline comments, npm run lint + cd cli && make lint must pass).

Codebase context (verified, trust this):

Stories are versioned markdown in story_version.code with embedded tags <chart query_id="query_x" ... /> and <table query_id="query_x" ... />, parsed by apps/shared/src/story-segments.ts (splitCodeIntoSegments, parseChartAttributes, TAG_ATTRS).
A query_id resolves to SQL via the originating chat's message_part rows (toolInput.sql_query, optional database_id) — see getSqlQueriesByIds / getSqlQueriesFromCode / getSqlQueryById in apps/backend/src/queries/story.queries.ts.
SQL executes only in the Python FastAPI sidecar: executeRawSql in apps/backend/src/services/live-story.ts POSTs {sql, nao_project_folder, database_id?, env_vars?} to POST /execute_sql in apps/backend/fastapi/main.py, which runs it via Ibis (cli/nao_core/config/databases/) and returns {data, columns, dialect}. dialect is the warehouse type string (bigquery, snowflake, duckdb, postgres, mssql, clickhouse, databricks, trino, etc.).
Static stories render cached rows from message_part.toolOutput; live stories cache into story_data_cache.queryData; per-embed live fetch exists via story.getLiveQueryData({chatId, queryId}) → executeLiveQuery, consumed by apps/frontend/src/components/story-embeds.tsx (useLiveQueryData pattern with TanStack query).
Story UI: SegmentList in apps/frontend/src/components/story-rendering.tsx, embeds in story-embeds.tsx and components/side-panel/story-chart-embed.tsx / story-table-embed.tsx, page shell story-page-body.tsx, viewer side-panel/story-viewer.tsx. Existing client-side date-range filtering precedent: filterByDateRange in apps/frontend/src/lib/charts.utils.ts.
Table column metadata is filesystem-based: databases/type=.../database=.../schema=.../table=.../columns.md under the project folder; see getTableColumnsContent and getDatabaseObjects in apps/backend/src/agents/user-rules.ts.
sqlglot>=26 is already a dependency in cli/pyproject.toml. Do NOT use node-sql-parser for the rewrite (poor dialect coverage); it stays where it is (citations/allowlist).
The agent authors stories via the story tool: apps/backend/src/agents/tools/story.ts (docs/prompt) and apps/shared/src/tools/story.ts.
Design to implement:

Filter definition — new markdown tag, stored in the story code so it versions/shares/downloads like charts: <filter id="status" column="status" label="Status" type="select" table="db.schema.orders" charts='["query_a"]' /> — column required; type one of select, multi_select, date_range, number_range, search; table optional (fully-qualified, for disambiguation + options lookup); charts optional JSON array of query_ids for explicit linking (absent = auto-match all relevant charts). Add parsing to story-segments.ts as a new segment type, a builder in apps/shared/src/chart-block.ts style, and validation alongside story-validation.ts. Filter selections are viewer state only (React state + URL search params) — never persisted, never written to story_data_cache.

Relevance/binding computation (backend): new tRPC procedure (e.g. story.getFilterBindings) that, per story version, returns for each (filterId, queryId): not_applicable, output_column (filter column present in the query's result columns), or pushdown (column exists on a base table referenced by the query — determine referenced tables via sqlglot in the sidecar or from metadata, and check columns via columns.md). Explicit charts attr overrides auto-match. Cache per story version.

SQL rewrite in the FastAPI sidecar with sqlglot: extend POST /execute_sql with optional filters: [{column, table?, operator, values}]. Implement a rewrite module (new file under apps/backend/fastapi/, e.g. sql_filters.py) that parses with sqlglot using the connection's dialect and:

if the column is in the outer projection → wrap: SELECT * FROM (<original>) AS _nao_f WHERE <predicate>, hoisting any trailing outer LIMIT/TOP outside the wrapper;
otherwise → pushdown: replace the matching exp.Table node (including inside CTEs) with a filtered derived table (SELECT * FROM t WHERE <predicate>) AS <original alias or table name> so the predicate applies before joins/GROUP BY;
build predicates with sqlglot expression builders (proper quoting/escaping per dialect, no string concatenation); support =/IN for select types, BETWEEN/>=/<= for ranges (dates and numbers), ILIKE/LIKE '%v%' for search;
on parse failure, raise a distinct error so the caller treats the filter as not applicable instead of failing the story. Write thorough pytest unit tests for this module across at least duckdb, bigquery, snowflake, postgres, mssql dialects, covering: column in projection, pushdown through joins, pushdown inside CTEs, GROUP BY queries (KPI-style single-row aggregates), LIMIT hoisting, quoted identifiers, and parse-failure fallback.
Execution endpoint: new tRPC procedure story.getFilteredQueryData({chatId, queryId, filters}) (mirror getLiveQueryData / executeLiveQuery in live-story.ts, passing filters through to FastAPI). Keep the existing isReadOnlySqlQuery guard on the original SQL. Add the equivalent for shared stories in shared-story.routes.ts if straightforward; otherwise leave shared stories unfiltered and note it.

Frontend: a filter bar rendered above the story content (in story-page-body.tsx / StoryViewer / StoryPreview) built from the parsed filter segments — shadcn components, matching the existing UI style. A context provider holds active selections. Each chart/table embed consults the bindings: with an active relevant filter, static stories with output_column binding filter client-side over cached rows (fast path, like filterByDateRange); otherwise fetch via getFilteredQueryData keyed by (queryId, hash(filters)), debounced, with a loading state and soft per-embed error fallback to unfiltered data. select/multi_select options: distinct values from cached result rows when the column is in the output; otherwise via a SELECT DISTINCT <column> FROM <table> LIMIT 100 through the sidecar when table is set.

Agent authoring: update the story tool docs/prompt (apps/backend/src/agents/tools/story.ts, apps/shared/src/tools/story.ts) so the assistant knows the <filter> tag syntax and when to add filters. Make the TipTap editor (side-panel/story-editor.tsx, preprocessForEditor) preserve filter tags without corrupting them (a read-only chip/node is enough; full filter-editing UI is out of scope).

Non-goals: don't touch refreshStoryData's unfiltered caching or the isLiveTextDynamic LLM rewrite (they always use unfiltered data); no new DB tables; no MCP embed support (mcp_query_data has no SQL text).

Testing requirements: pytest for the sqlglot rewrite module; vitest for story-segments filter parsing and binding logic; then end-to-end manual verification — run the app (npm run dev:backend, npm run dev:frontend, and npm run dev:fastapi with a DuckDB-based nao project so SQL actually executes), create a story with 2+ charts sharing a filterable column (one chart where the column is in the SELECT, one KPI-style aggregate where it isn't, to prove pushdown), add a filter, and record a video showing the filter updating both charts. npm run lint and cd cli && make lint must pass.
