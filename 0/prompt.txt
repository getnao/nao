## Description

@beherap

beherap

opened on Jul 28, 2026

Issue body actions

Summary

Concurrent MCP server discovery (startup or config reload) races on runtime creation: each server's \_ensureRegistered sees `this._runtime == null`, builds its own runtime, and overwrites the previous one. Servers registered on an overwritten instance are lost, and all later refreshes and tool calls for them fail instantly with `Unknown MCP server '<name>'`.

Environment

* getnao/nao:0.3.0 (Docker) — also reproduced after rebuild; the same code is in current main (apps/backend/src/services/mcp.ts)
* 3 stdio servers in agent/mcps/mcp.json (affects any config with ≥2 non-OAuth servers; transport-independent — one of ours is a plain stdio server, two use mcp-remote)

Reproduction

1. Configure 2+ servers in agent/mcps/mcp.json.
2. Start the container with no spec dirs under agent/mcps/ (forces parallel discovery), or touch mcp.json to trigger \_reloadAndDiscover.
3. Click refresh on a server in the MCP settings panel, or let the agent call one of its tools.
4. Some subset of servers fails with Unknown MCP server '' in \~30 ms. Which server fails varies per run (whoever's createRuntime() resolves last "wins").

Log signature: `[ERROR] [tool] MCP discovery failed: <name> / MCP tool call failed: <name>/<tool> with the error Unknown MCP server '<name>'.`

Root cause

\_ensureRegistered has a check-then-act race:

```
private async _ensureRegistered(name: string): Promise<void> {
    if (!this._runtime) {
        this._runtime = await createRuntime();   // N concurrent callers → N runtimes, last write wins
    }
    if (this._registered.has(name)) {
        return;                                  // sta a discarded runtime
    }
    ...
}

```

All parallel discoveries pass the !this.\_runtime check before any assignment resolves. Each registers its server on whichever instance is current at its own resolution time; \_registered accumulates all names, so subsequent calls skip re-registration and hit the surviving runtime, which never saw the definition.

Related: this code path replaced the per-call runtime from #202 (fixed in #1049) — same symptom, new mechanism.

Suggested fix

Memoize the in-flight createRuntime() so concurrent callers share one runtime

```
private _runtimePromise: Promise<Runtime> | null = null;

private async _ensureRegistered(name: string): Promise<void> {
    if (!this._runtime) {
        if (!this._runtimePromise) {
            this._runtimePromise = createRuntime().catc
                this._runtimePromise = null;
                throw error;
            });
        }
        this._runtime = await this._runtimePromise;
    }
    ...
}

```

Verified in our deployment: with this change, parallel rediscovery of all 3 servers completes cleanly and tool calls succeed; unpatched, at least one server fails every reload. Happy to send this as a PR.
